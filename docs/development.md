## 实现约束

- macOS：CaptureModel 负责 UI 状态，CaptureEngine 串行处理媒体，MovieWriter 负责每路 H.264/AAC 写入。
- RecordingMode 是所选机位的唯一来源，权限申请、采集启动、健康检查、收尾与报告均遵循选择。
- 预览从成功 append 的视频样本创建独立的即时显示样本包装，共用像素缓冲区，不改变录制样本元数据。通过 NSViewRepresentable 中的 AVSampleBufferDisplayLayer 连续显示，移除 CoreImage 静帧缩放和一秒限频；每路最多一个待送 UI 的任务，渲染器不就绪则丢弃预览帧。
- 每路预览使用独立 ObservableObject，避免每帧刷新整窗控件。UI 使用原生视频显示层按区域缩放像素；折叠时关闭帧传递，录制继续。每次开始及停止隔离异步回调，旧图不能覆盖新 Take。
- 不引入网络依赖、服务器、登录、遥控和远程卸载。
- macOS 现阶段 UI 与录制同进程；已实现中断素材扫描及重封装副本，仍不能保证断电或强杀前所有内容可恢复，不声称已具备生产稳定性。

## L2 本轮实现（2026-10-21）

- 设置面板选择摄像头、话筒和显示器；默认在开始时解析系统设备。明确选定的设备失联则报错，不自动切换。设备列表支持手动刷新，录制期间禁止更换。
- 录制期间持有系统活动，防止闲置睡眠；捕获会话中断、运行错误、系统即将睡眠时进入保存流程。强制睡眠和掉电不能保证及时完成保存。
- 每秒检查编码器与剩余空间；静态桌面每秒至多补一次保持帧，使碎片封装继续推进。保留原有 8 Mbps 摄像头和桌面像素/码率策略。
- 首片间隔目标 1 秒、后续 10 秒，实际以编码器/关键帧及磁盘提交为准，不保证只损失固定秒数。
- 每个 Take 持有进程级文件锁；崩溃后操作系统释放。恢复扫描跳过正在录制、正在恢复、正常封装及已恢复的素材。
- 设置中“恢复副本”对有报告的未完成 Take 逐路重封装到独立 Recovered-UUID 目录；检查双轨、正时长及首尾画面解码。原 MP4 不覆盖、不删除。缺少已落盘片段、数据损坏或空间不足时明确报错。
- Windows 环境预检与桌面诊断脚本位于 script；保留早期诊断记录；新客户端实现见下节。

后续验收重点：真实双路录制两小时、会议设备共用、拔设备/拔外盘、睡眠后检查、恢复副本 FCP 导入和长时同步。不要拿合成媒体检查替代这些结论。


## Windows 桌面客户端（2026-10-21）

`clients/windows` 使用 .NET 8 WinForms 与系统 WASAPI，未添加 NuGet 依赖。GDI 采集所选显示器，libx264 软件编码原像素 30 fps；按 1080p 12 Mbps 等比例设定目标码率。默认主屏及开始时的系统播放设备，允许明确选择播放设备，不打开摄像头或话筒。

音频按 QPC 时间戳写 RF64，补齐静音，并以桌面首帧时间对齐。停止后复制视频流并编码 AAC 生成 desktop.mp4，同时保留分离视频和原始声音。碎片 MP4 与 RF64 定期写入降低异常丢失范围，但不保证断电可恢复；Windows 自动恢复入口尚未实现。保存阶段需要额外空间。

右上角小窗排除采集，同源 10 fps 预览支路连续显示；折叠停止 UI 帧传递和解码，编码器预览支路仍运行。设备切换在录制期间锁定；睡眠、显示配置变化、音频失败、编码器退出和磁盘余量不足进入停止并保留素材流程。真实故障验收范围见 validation.md。

构建和自检命令见 [Windows 说明](../clients/windows/README.md)。当前驱动不兼容此次 FFmpeg 的 NVENC API，因此使用软件编码，不更改用户显卡驱动。
