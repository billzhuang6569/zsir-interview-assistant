## 实现约束

- macOS：CaptureModel 负责 UI 状态，CaptureEngine 串行处理媒体，MovieWriter 负责每路 H.264/AAC 写入。
- RecordingMode 是所选机位的唯一来源，权限申请、采集启动、健康检查、收尾与报告均遵循选择。
- 预览从成功 append 的视频样本创建独立的即时显示样本包装，共用像素缓冲区，不改变录制样本元数据。通过 NSViewRepresentable 中的 AVSampleBufferDisplayLayer 连续显示，移除 CoreImage 静帧缩放和一秒限频；每路最多一个待送 UI 的任务，渲染器不就绪则丢弃预览帧。
- 每路预览使用独立 ObservableObject，避免每帧刷新整窗控件。UI 使用原生视频显示层按区域缩放像素；折叠时关闭帧传递，录制继续。每次开始及停止隔离异步回调，旧图不能覆盖新 Take。
- 不引入网络依赖、服务器、登录、遥控和远程卸载。
- macOS 现阶段 UI 与录制同进程；已实现中断素材扫描及重封装副本，仍不能保证断电或强杀前所有内容可恢复，不声称已具备生产稳定性。

## L2 本轮实现（2026-10-21）

- 设置面板选择摄像头、话筒和显示器；默认在开始时解析系统设备。明确选定的设备失联则报错，不自动切换。设备列表支持手动刷新，录制期间禁止更换。
- 录制期间持有系统活动，防止闲置睡眠；捕获会话中断、运行错误、系统即将睡眠时进入保存流程。强制睡眠和掉电不能保证及时完成保存。
- 每秒检查编码器与剩余空间；静态桌面每秒至多补一次保持帧，使碎片封装继续推进。保留原有 8 Mbps 摄像头和桌面像素/码率策略。
- 首片间隔目标 1 秒、后续 10 秒，实际以编码器/关键帧及磁盘提交为准，不保证只损失固定秒数。
- 每个 Take 持有进程级文件锁；崩溃后操作系统释放。恢复扫描跳过正在录制、正在恢复、正常封装及已恢复的素材。
- 设置中“恢复副本”对有报告的未完成 Take 逐路重封装到独立 Recovered-UUID 目录；检查双轨、正时长及首尾画面解码。原 MP4 不覆盖、不删除。缺少已落盘片段、数据损坏或空间不足时明确报错。
- Windows 环境预检与桌面诊断脚本位于 script；保留早期诊断记录；新客户端实现见下节。

后续验收重点：真实双路录制两小时、会议设备共用、拔设备/拔外盘、睡眠后检查、恢复副本 FCP 导入和长时同步。不要拿合成媒体检查替代这些结论。


## Windows 桌面客户端（2026-10-21）

`clients/windows` 使用 .NET 8 WinForms 与系统 WASAPI，未添加 NuGet 依赖。GDI 采集所选显示器，libx264 软件编码原像素 30 fps；按 1080p 12 Mbps 等比例设定目标码率。默认主屏及开始时的系统播放设备，允许明确选择播放设备，不打开摄像头或话筒。

音频按 QPC 时间戳写 RF64，补齐静音，并以桌面首帧时间对齐。停止后复制视频流并编码 AAC 生成 desktop.mp4，同时保留分离视频和原始声音。碎片 MP4 与 RF64 定期写入降低异常丢失范围，但不保证断电可恢复；Windows 自动恢复入口尚未实现。保存阶段需要额外空间。

右上角小窗排除采集，同源 10 fps 预览支路连续显示；折叠停止 UI 帧传递和解码，编码器预览支路仍运行。设备切换在录制期间锁定；睡眠、显示配置变化、音频失败、编码器退出和磁盘余量不足进入停止并保留素材流程。真实故障验收范围见 validation.md。

构建和自检命令见 [Windows 说明](../clients/windows/README.md)。当前驱动不兼容此次 FFmpeg 的 NVENC API，因此使用软件编码，不更改用户显卡驱动。

### 用户流程

1. **欢迎与选择方式**：第一次运行先显示原生引导窗口，说明“先完成权限设置，点击开始录制后才会采集，素材保存在本机”。复用摄像头 / 桌面 / 双路选择，默认与现有双路一致。
2. **逐项授权**：显示当前方式所需的权限卡片，每项包括用途、文字状态和一个明确操作按钮。摄像头用于人物画面、话筒用于摄像头素材声音；桌面授权用于屏幕与系统播放声音。未选机位无需授权。
3. **完成设置**：重新检查所需权限，通过后显示“权限设置完成”，点击“进入录制小窗”；不自动开始、不承诺设备或音视频质量已经验收。未通过项可重试、返回调整录制方式，或选择“稍后设置”。

所有授权仅在用户点击对应按钮时串行请求；已授权项直接显示完成，不重复弹窗。不在引导内增加设备预览、试录、音量表、登录或邀请码。

### 状态与再次进入

| 场景 | 行为 |
| --- | --- |
| 摄像头/话筒尚未询问 | 显示“允许摄像头/话筒”，点击后触发系统弹窗 |
| 已拒绝 | 显示“打开系统设置”及手动路径；不循环请求 |
| 系统/组织限制 | 说明无法在应用中解除，提示联系设备管理员，可返回改录制方式 |
| 已授权 | 显示文字与图标，进入下一项 |
| 屏幕权限无法细分原因 | 显示“尚未确认授权”，不要把布尔预检失败臆断为首次拒绝或系统限制 |
| 从设置返回 / 点击重新检查 | 重新读取系统状态，保留当前进度；不会再次主动弹出授权请求 |
| 系统要求重新打开应用 | 显示退出并重新打开的说明，保留所选方式；不自动杀进程、不在忙碌时退出 |
| 点击稍后设置 | 回到小窗，不记为已完成；本次启动不反复弹出，下次启动继续引导 |
| 中途退出 | 下次从未完成设置恢复，系统状态重新读取 |
| 完成后再次启动 | 不重复欢迎页；设置中始终有“权限设置”入口 |
| 完成后撤权 / 切换方式缺权限 | 开始前显示缺失项并进入相应引导；不重新跑全部欢迎页 |
| 老版本升级且没有引导记录 | 首次升级进入引导；已有授权自动识别，可直接完成，不清空原配置 |

持久化仅保存引导完成标志及所选录制方式（必要的重开进度），不缓存授权真值；单路完成后重新启动必须保持该方式，避免恢复为双路又索要额外权限。复用 UserDefaults，不建立新配置格式。异步授权期间禁用重复点击及方式切换；关闭后到达的回调不得自动重开窗口或开始录制。

### 系统接口与限制

摄像头/话筒使用现有 AVFoundation，按系统 authorizationStatus 区分未询问、允许、拒绝、受限，仅未询问时请求；参见 [Apple 授权文档](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media)。

屏幕授权先验证系统预检/请求接口在最低 macOS 14 与当前系统、实际 .app 身份下的行为，再接入现有 ScreenCaptureKit 路径；不能通过开始录制或创建 SCStream 偷做权限检测。引导只表达权限状态，系统声音实际可录仍由真实采集验收判断。系统设置的名称随版本变化，参考 [Apple 屏幕与系统音频设置说明](https://support.apple.com/en-gb/guide/mac-help/mchld6aa7d23/mac)。

“打开系统设置”优先尝试对应隐私面板，实施时实测跳转兼容性；若只打开设置首页或失败，仍展示“系统设置 → 隐私与安全性 → 对应权限”的手动步骤。不能承诺程序自动开启开关。无需辅助功能、自动化、全磁盘访问或修改 TCC 数据库。

现有 ad-hoc 签名重新构建后可能需要重新授权；保留真实状态检测，不通过更换 bundle identifier 解决。签名、公证和 Gatekeeper 属于另一个发行事项，不混入本计划。

### 验收与检查

- 无硬件断言：三种模式权限映射；未询问/允许/拒绝/受限/未知；重复点击；返回设置刷新；关闭后的迟到回调；完成、跳过与中断的持久化；升级、撤权及模式切换；busy 下禁止进入或退出。
- 真机：使用独立测试用户或专用测试环境验证首次授权，不重置日常录制应用的权限。通过打包 .app 验证 TCC 身份，而不是把终端的授权当作应用授权。
- macOS 14 与当前开发系统分别记录：三种模式逐步允许、拒绝再允许、返回设置、系统要求重开、权限已存在、升级后首次引导、设置重入、键盘/VoiceOver。Apple Silicon 与 Intel 按实际机器留证，模拟或交叉编译不算真机通过。
- 引导期间确认无设备采集、无新 Take / report / MP4；完成后仍等待用户点击开始。随后三种模式各做短录制，验证相应音视频产物及未选机位不采集。
- 回归录制中收起/展开、停止保存、恢复过程和退出保护；撤权后的采集错误仍保留素材。
- 实现后最小检查：`swift run --package-path clients/macos ZSirCapture --check-recording-ui`、`swift run --package-path clients/macos CaptureChecks`，并在应用空闲退出后构建 .app 验证。不能用模拟断言替代 TCC 实测。

交付顺序：本计划 PR 评审 → 实施与状态自检 → 真机权限和短录制验收 → 单独决定合并与下一版发行。计划 PR 用 Refs 关联 issue，合并计划不关闭功能 issue。
