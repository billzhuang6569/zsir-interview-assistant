# 0.4.0 recording contract and diagnostics

Groundwork for #38 under milestone #37. This contract has no dependency on #35 or #36. It specifies the shared behavior for the existing macOS and Windows clients; platform adoption and real-device acceptance must be recorded separately.

## Scope and compatibility

Preserve camera-only, desktop-only, and dual recording; native desktop pixels; existing quality choices; selected audio tracks; unique Take directories; fragmented media and recovery that preserves originals. Keep macOS 12.3+ compatibility. The macOS 12 compatibility edition continues to disable system audio even on newer systems; macOS 13+ full edition retains its system-audio path. No maintenance path is added for systems below macOS 12.3. Windows keeps its existing supported runtime and capture stack.

## Clock and output timeline

Each Take owns one monotonic epoch. Map source timestamps into that epoch before admission. Wall-clock time is metadata only. Each selected video output has integer frame indices n = 0, 1, 2, … at exactly 30 frames/second: presentation time n/30 seconds and duration 1/30 second. Use rational media timestamps (CMTime(value: n, timescale: 30) on macOS), not accumulated 33,333,333 ns delays. Integer nanoseconds are scheduling adapters only; derive each deadline independently with checked arithmetic.

The first usable captured frame establishes availability. Do not count timer activity as capture or invent a black startup frame. At a tick, select the most recent eligible source frame; retain one image for static desktop ticks. A repeat uses the same pixels with a fresh timestamp and duration. Do not mutate source sample attachments. Audio keeps its source sample-rate timeline against the same Take epoch; video repetition must never duplicate audio. A capture gap and an encoder stall are different events: a static source may legitimately repeat; encoder rejection must be counted and surfaced.

Stop establishes one shared end boundary. Reject subsequent capture arrivals, cancel scheduling, drain admitted work, then end selected tracks at that boundary and finalize once. Do not append beyond the stop boundary. A selected track with no usable samples cannot report a successful save. Finalization failure leaves the Take recoverable and reports the failing track. Reset clock, held frames, queues and diagnostics before the next Take.

## Ownership and bounded work

Capture callbacks only normalize/offer samples and update capture counters; they must not wait on disk, UI or encoder readiness. One serialized owner per track controls held frames, scheduling, writer admission and diagnostic mutation. All access to the pure bounded ring must be serialized by that owner; the helper supplies no lock.

Recording admission uses a fixed-capacity ring (initial video capacity: 3). Full admission rejects the incoming item, increments backpressure and retains already admitted ordering. Count every rejection; no unbounded callback or task backlog may precede the ring. A delayed scheduler computes the current index directly and counts skipped ticks as late, instead of enqueueing every missed deadline. Writer readiness failure increments backpressure without blocking capture. Persistent inability to maintain the timeline must become a visible recording error; successful CFR acceptance requires contiguous written frame timestamps. Exact stall thresholds belong to platform integration and must be documented with that implementation.

Preview is independent: one pending latest image per preview surface, at most 10 updates/second. Replacing a pending image increments preview drops. Preview starts/stops with its own lifecycle, releases held buffers on hide/stop, and cannot start a Take, change recording timestamps or hold the recording queue. Thumbnail/settings preview uses the same ownership rules. Device/source changes invalidate the old generation before starting a replacement so stale callbacks cannot publish into a new session.

## Diagnostics and evidence

Persist a per-track final snapshot in the existing Take report alongside state/error metadata; runtime UI may consume copied snapshots at a bounded rate. Keep counters per Take and preserve them on failure:

| Field | Meaning |
| --- | --- |
| capturedFrames | New eligible source video frames received, excluding timer ticks and repeated images |
| scheduledFrames | Output ticks admitted for encoding, including repeats |
| writtenFrames | Frames successfully appended to the writer |
| repeatedFrames | Admitted ticks using the previously held source image |
| lateFrames | Output tick deadlines skipped because scheduling was late |
| backpressureFrames | Recording frames rejected by queue capacity or writer readiness; one count per rejected frame |
| previewDroppedFrames | Pending preview images replaced or discarded for preview rate limiting |
| queueDepth | Current pending recording items |
| queueHighWaterMark | Maximum pending recording items during this Take |

Counters measure different stages and need not sum to one another while work is pending. Never infer new capture FPS from writtenFrames: a static desktop can have one captured image and 300 written frames in ten seconds. Report observation duration and derive each rate from its matching counter. Inspect actual encoded frame timestamps, track presence, dimensions, duration, decode success and audio alignment for acceptance; diagnostics alone do not prove media correctness.

`clients/macos/Sources/RecordingCore/RecordingContract.swift` contains dependency-free timeline conversion, a bounded ring and serializable diagnostic values. These helpers do not activate or change either platform's pipeline. Standalone checks are in `clients/macos/ContractChecks/main.swift`; from `clients/macos`, run:

```sh
swiftc Sources/RecordingCore/RecordingContract.swift ContractChecks/main.swift -o /tmp/zsir-contract-checks
/tmp/zsir-contract-checks
```

The checks cover 24-hour rational timing without accumulated drift, invalid/overflow inputs, queue saturation and wraparound, ordering and diagnostic JSON round-trip. macOS framework checks, Windows builds and device recording require their respective hosts. Linux without Swift cannot execute the Swift checks; no platform recording validation is implied by a source review.
