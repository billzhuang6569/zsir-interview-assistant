## 音源契约

- `desktop.mp4`：选中的系统输出设备/系统声音，无话筒混入。
- `camera.mp4`：选中的话筒，无系统音轨混入。
- 双路录制分别保持上述路由，诊断报告记录每路音源。
- 麦克风在物理上可能收到扬声器声音，路由测试要戴耳机，避免把物理回声误认成串轨。
- 验收先只播放系统标记声并使话筒安静，再只向话筒发声，逐文件检查；再做同时标记与首中尾同步。
- 现有关闭系统声音设置与 macOS 12.3 兼容包会生成无系统音轨桌面。兼容包当前不能满足带系统声音的 desktop 要求；没有将其计为已通过或静默替换为话筒。

## #62 本轮修复与证据

本机 11月19日多次报告：desktop、native、compact、5120×2880、systemAudio=true，约0.34–0.38秒即失败，videoSamples=0。原始 Take 保持不变。

使用 MovieWriter 和同样 NV12 5K 画面、码率复现：AVFoundation -11800，底层 NSOSStatus -12903。此证据说明本机同尺寸路径失败，不断言所有 -11800 都是同一原因。

超过4096像素的任一边使用硬件 HEVC，其他尺寸继续 H.264；不降低原生尺寸。报告记录实际 codec，错误保留最多8层底层错误码。5K 回归验证30帧、逐帧时间戳、完整视频解码与 AAC 音轨存在；全套现有录制核心检查通过。原生5K的 HEVC 在旧剪辑软件/旧硬件上的导入仍需验证。

证据：`docs/testing/stability-2026-11-20/5k-before.txt`、`core-checks.txt`。这些都是合成输入，不代表真实系统采集或飞书已通过。

## Windows 共享采集与 camera 恢复实现（本轮续做）

用户要求先完成实现，等办公室测试机开启后再执行实机测试。本轮没有连接或启动远程摄像头。

### 实现范围

- 摄像头枚举改为 Windows DeviceInformation；已有 DirectShow PnP 设备ID按前缀/大小写匹配，不静默切换到其他摄像头。
- MediaCapture 只启用 Video + SharedReadOnly + CPU memory；MediaFrameReader 返回固定大小 BGRA。没有调用设备 SetFormatAsync 或回退到独占 DirectShow。转换只作用于本应用的reader。
- 主界面预览、设置预览、录制、设备诊断使用同一共享输入实现。麦克风继续使用 WASAPI共享模式，desktop仍使用系统输出设备。
- BGRA通过仅当前用户可访问的随机命名管道送入既有FFmpeg；一个在写帧加一个待写帧，慢消费者替换待写帧，使用数组池。不在采集回调等待编码器/磁盘。
- 输入时间戳继续采用FFmpeg的wallclock路径，与现有Unix/QPC音频对齐和时钟跳变保护配合；真实端到端延迟与同步必须实机测量。不能把离线样本当作新后端同步已通过。
- 启动/停止保留实际native任务的所有权。取消后等待晚到初始化再释放；停止超时后保留清理任务和Take排他锁。预览在实际清理完成前不交接源。
- 摄像头子Recorder现在单独写 `camera-report.json`；包括起始时间、音源、共享模式、源帧/队列丢帧计数和底层错误。未声称这些计数包含驱动内部丢帧。
- 恢复分别扫描 `desktop-video.mp4 + system-audio.wav` 和 `camera-video.mp4 + microphone.wav`。优先使用camera独立报告，兼容旧版camera-only主报告和双路报告内的逐轨时钟。
- 缺失/损坏/异常时钟时只生成明确标为needs_review的视频副本，保留原音频，不猜测音画起点。已有完整成片不覆盖，原文件/报告不修改，使用Take排他锁防止处理活动素材；一路恢复失败仍尝试另一路，并汇总错误。
- 支持目标保持Windows10 2004+/11 x64、Win11 ARM64；项目使用Windows SDK .NET投影，包含其notice。ARM64仍使用x64 FFmpeg仿真。
